Reference

Configuration and internals

Everything you need to point it at a real Prometheus, teach it your own metric names, and know where it will let you down.

Configuration

Read from .env in the project root, or from the environment directly. A real environment variable always wins over the file.

Variable Default What it does
PROMETHEUS_URL — Required. Base URL of the Prometheus HTTP API, with no trailing /api/v1. The process exits with an explanation if unset.
PROMETHEUS_TOKEN empty Sent as Authorization: Bearer …. Leave unset for an unauthenticated Prometheus.
PORT 8787 Port the API listens on. The Vite dev server reads it too, so PORT=8788 npm run dev runs a second instance whose UI talks to its own API.
PORT_TAKEOVER 0 Set to 1 to stop an existing server holding that port instead of failing. Only stops a server started from the same directory. npm run dev:takeover sets it for you.
PROMETHEUS_TIMEOUT_MS 30000 Raise it if long range queries against a busy server are timing out.
PROMETHEUS_HEADERS empty Extra headers as JSON, for proxies that need them — for example {"X-Scope-OrgID":"team-payments"}.
PROMETHEUS_INSECURE 0 Set to 1 to skip TLS verification. Disables the check for the whole process — only for a self-signed certificate on a network you trust.
CATALOG_TTL_SECONDS 300 How long the metric catalogue is cached. It changes rarely and is expensive to fetch.
The token stays server-side

All Prometheus traffic goes through the Node process, and the browser only ever calls this app's own /api. In production a single process serves both the API and the built UI, so there is no cross-origin surface at all.

How resolution works

The hard problem is that no two services name anything the same way. Spring Boot calls the HTTP path uri; the Prometheus Java client calls it handler; OpenTelemetry calls it http_route. A tool that hardcodes any one of those works for exactly one stack.

So investigations are written against abstract signals — http.requests.count, db.pool.pending, jvm.gc.pause.sum — and a registry maps each signal to candidate metric names per convention, in preference order. The first candidate that exists wins.

Resolution folds every candidate into a single instant query, so one round trip establishes both which metrics exist for this target and how many series each has: 

count by (__name__) ({__name__=~"a|b|c", job="checkout-api"})

Candidates are checked against the cached catalogue first, so the regex only ever contains names that exist somewhere. Signals that share a family are forced to resolve to the same convention — otherwise a count from Micrometer and a histogram from OpenTelemetry would disagree about what the label for "route" is called.

The three scopes

Not everything lives under the job you picked.

Scope Scoped by Examples
target The job you chose HTTP metrics, JVM metrics, connection pools — your app's own endpoint
dependency A job you choose on the card redis_exporter, postgres_exporter
infra Derived namespace and pod cAdvisor, kube-state-metrics

The infra scope is the interesting one. Container metrics scrape under cAdvisor's own job, so job="your-app" will never match them — they are keyed by namespace and pod. The app asks Prometheus which namespace and pods your application's own series carry, and builds a selector from that.

If your metrics carry no such labels, these signals are reported as gaps with an explanation. That is deliberate: matching without them would silently pull in every container in the cluster and produce numbers that look plausible and are wrong.

Teaching it your metric names

If an investigation shows as unavailable but you know the data exists, add a candidate to the relevant signal in src/server/signals.ts:

{
  id: 'http.requests.count',
  candidates: [
    // …existing entries…
    {
      flavor: 'My framework',
      metric: 'myapp_http_requests_total',
      labels: { route: 'endpoint', status: 'status_code', method: 'verb' },
      errorPattern: '5..',
    },
  ],
}

Three things to get right:

  • Order is preference. Put your entry where you want it considered — the first candidate present in your Prometheus wins.
  • Map the label roles. Panels ask for roles like route and status, never for literal label names. A role you leave out simply disables the panels that need it, rather than breaking anything.
  • Match the family. If you add a candidate for http.requests.count, add the matching one for http.latency.histogram under the same flavor string, or the family rule will fall back to a different convention.

Add scale if your metric is in different units — the legacy OpenTelemetry candidate uses scale: 0.001 to convert milliseconds to seconds — and matchers for any filter the metric always needs.

Troubleshooting

"Prometheus returned a non-JSON response"

PROMETHEUS_URL is pointing at a UI path rather than the API root. It should be the bare origin, with no /graph and no /api/v1.

"Prometheus rejected the bearer token"

The token is wrong or expired. If your Prometheus sits behind a proxy that wants a different header entirely, use PROMETHEUS_HEADERS instead.

"Port 8787 is already in use"

Something already holds the port — usually a server you left running in another terminal. The message names the process and gives you three ways out: npm run dev:takeover stops it and takes the port, PORT=8788 npm run dev runs alongside it on its own port, or you stop it yourself with the kill command shown.

Takeover only ever stops a server started from the same directory. If the port belongs to anything else it is reported and left running, even with PORT_TAKEOVER=1 set. And if the port is grabbed again immediately after being freed, something is supervising it — usually another npm run dev — so stop that terminal rather than the child process.

Vite says "Port 5173 is in use, trying another one"

Harmless. Vite steps to the next free port and prints the real one; its API proxy is unaffected. Open whichever URL it prints.

The first page load is slow

Target discovery runs count by (job) ({__name__=~".+"}), which touches every series in the TSDB. On a very large Prometheus that is genuinely expensive. It is not cached between restarts.

Every investigation says "not available"

Usually the wrong job. Application metrics and container metrics live under separate jobs — pick the one scraping your app's own /metrics endpoint, not cadvisor or kubernetes-nodes.

The numbers look wrong

Open Metrics this used at the bottom of the report and check what each signal resolved to. A signal matching a metric you did not expect means the report is measuring the wrong thing.

Latency percentiles are missing

Histogram buckets are off. In Spring Boot: management.metrics.distribution.percentiles-histogram.http.server.requests=true. Without buckets, percentiles cannot be computed at all — a _count and _sum only give you an average.

Known limitations

Worth knowing before you rely on it.

Coverage

The signal registry is a curated allowlist. It recognises the conventions that were written into it and nothing else, so an unusual naming scheme reads as "not available" even though the data is there. Adding a candidate fixes it permanently, but it does not discover conventions on its own.

Calibration

Thresholds are universal; systems are not. "p99 above one second" is meaningless for a batch job. The findings are opinionated defaults, not calibrated to your SLOs, and they are not configurable yet.

No synthesis across domains

Each investigation is scoped to its own domain. Service health does not know the connection pool is saturated. Connecting findings across investigations is still the reader's job.

Level, not change

Everything is "over the last N". There are no deploy markers and no week-over-week comparison, so a service that broke a month ago looks the same as one that broke ten minutes ago — even though diagnosis is usually about what changed.
