Architecture

How it works

Three pictures cover most of it: what talks to what, how a plain-language question turns into PromQL that matches your metric names, and why some metrics are matched by job while others are matched by pod.

The shape of it

One Node process sits between the browser and Prometheus. It is not a passthrough proxy — the browser never names a metric or writes a query. It asks for an investigation, and gets back a finished report.

How a question becomes a query

This is the part that makes the same investigation work on services instrumented differently. Playbooks never mention a metric name. They ask for a signal — http.requests.count — and the resolver works out what your Prometheus calls it.

Why one query

Probing 87 metric names individually would be 87 round trips on every page load. Candidates are first filtered against the cached metric catalogue, so the regex only ever contains names that exist somewhere, and the result doubles as a cardinality check.

Three scopes

Picking a job is not enough, because the metrics that describe a service are not all scraped from it. This is the single most common source of confusion, and the reason the app asks for a job and sometimes an exporter.

When derivation fails

If your application's metrics carry no namespace or pod label, there is no honest way to connect them to container metrics. Those signals are then reported as gaps with an explanation, rather than matched cluster-wide — which would produce plausible numbers describing the wrong containers.

Where each part lives

File Responsibility
server/config.ts Reads and validates the environment. Exits with an explanation if unusable.
server/prom.ts The only place that talks to Prometheus. POSTs queries, GETs metadata, attaches auth, turns NaN into a genuine gap rather than a zero.
server/catalog.ts Cached metric catalogue, job discovery, selector building and escaping, and the namespace/pod derivation behind the infra scope.
server/signals.ts The registry: abstract signals, candidate metric names per convention, label-role mapping. This is the file you extend for a stack it does not recognise.
server/playbooks/ One file per investigation. Each panel declares what it needs, builds its PromQL, and carries the rule that turns its numbers into a sentence.
server/engine.ts Resolve, filter panels to what can run, execute with bounded concurrency, interpret, roll up to a verdict.
server/capabilities.ts The audit behind the in-app Help page: the whole registry, checked against this Prometheus.
web/ The wizard and the Help page. Charts are hand-authored SVG — no chart library.

The dependency arrow only ever points one way: playbooks → signals → catalog → prom. A playbook cannot reach Prometheus directly, which is what keeps a panel definition to a query and a threshold.
