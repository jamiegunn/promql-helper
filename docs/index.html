Documentation

Ask a question. Get an answer.

PromQL Helper is a diagnostic wizard for Prometheus. You pick a question about your service — the kind you would actually ask out loud — and it works out which of your metrics can answer it, runs the queries, and tells you what it found.

One investigation, end to end

Is this service serving happy users?

checkout-api · matched via Micrometer

  • http.requests.count → http_server_requests_seconds_count
  • http.latency.histogram → http_server_requests_seconds_bucket
  • http.latency.sum → http_server_requests_seconds_sum
▲ Needs attention /api/checkout is the slowest endpoint at 4.50s (p99), and 2 other findings.

The three lines in the middle are the part that makes this work: what the investigation asks for on the left, and what your Prometheus actually calls it on the right.

You never write any PromQL. It is there if you want it — every panel has a PromQL button that shows the exact query and copies it — but the queries are generated for you, and the results are read for you.

What it does

Most monitoring tools show you metrics and leave the diagnosis to you. This one starts from the diagnosis. The five investigations are written the way an on-call engineer actually thinks:

  • Is this service serving happy users? Traffic, failure rate and latency percentiles, broken down by endpoint.
  • How much CPU and memory does it use, and how spiky is it? Usage over time with a percentile breakdown, checked against the limits on the pod — including whether those limits are throttling it.
  • Is the Java runtime itself healthy? Heap pressure, garbage-collection overhead, and whether threads are blocked rather than working.
  • Is this app pummelling the database? Connection-pool saturation from the application side, checked against what the database server reports.
  • Is this app hammering Redis? Command throughput, cache hit ratio, evictions, and whether something is blocking the single Redis thread.

A question only appears if your metrics can answer it. Where they cannot, the card says what to instrument instead of failing silently.

Connect it

Two variables. That is the whole configuration.

# .env
PROMETHEUS_URL=https://prometheus.internal.example.com
PROMETHEUS_TOKEN=<bearer token>
npm install
npm run dev

The UI comes up on http://localhost:5173. For a single production process serving both the API and the UI, run npm run build && npm start and open http://localhost:8787.

Your token stays put

All Prometheus traffic goes through the Node process. The browser only ever talks to this app's own /api, so the bearer token is never sent to the client and never appears in a network tab.

PROMETHEUS_URL is the API root — no trailing /api/v1. Leave PROMETHEUS_TOKEN unset for an unauthenticated Prometheus. Everything else is optional and documented in Reference → Configuration.

The three steps

The wizard is a real sequence — each step narrows what the next one has to consider.

  1. Pick a service Choose one of the jobs Prometheus is scraping. Optionally narrow to a namespace or a single pod.
  2. Choose a question The app matches your metrics against what each investigation needs, and offers only the questions your data can answer.
  3. Read the answer It runs the queries, interprets the numbers, and leads with a verdict — the worst thing it found, in one sentence.

The walkthrough goes through all three with screenshots.

Try it with no Prometheus

The repository ships synthetic exporters and a scrape config, so you can see the whole thing work before pointing it at anything real: 

npm run demo

That starts the fixture exporters, a real Prometheus in Docker, the API and the UI. Set PROMETHEUS_URL=http://localhost:9090 and give it a minute or two to build up some history.

The fixture pretends to be a Spring Boot service called checkout-api running two pods, alongside Redis, Postgres, cAdvisor and kube-state-metrics. It has real problems baked in — a slow checkout endpoint, a connection pool that runs out, a Redis instance evicting keys — so there is something to actually find. Every screenshot in these docs comes from it.
